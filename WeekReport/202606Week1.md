## 2 文档格式自动化转换（pipeline/convert.py）

### 2.1 整体设计

新增 `pipeline/convert.py`，作为RAG流水线的第0步，实现从原始文档到标准化Markdown的全自动转换。文件组织采用"inbox入库"模式：

```
知识库文件 → convert.py转化为md格式 → clean.py清洗数数据 → chunk.py切片 → embed.py向量化 → ChromaDB向量数据库存储
```

原有 `clean.py → chunk.py → embed.py` 下游流程不变。各格式对应工具如下：

| 格式 | 工具 | 说明 |
|------|------|------|
| `.pdf`（文字版） | `pymupdf4llm` | 保留标题层级、表格结构，原生支持中文 |
| `.pdf`（扫描版） | `RapidOCR` | 输出不足200字符时自动切换，fitz逐页渲染后识别 |
| `.pdf`（字体乱码） | `RapidOCR` | 检测到乱码特征时自动切换（见2.2） |
| `.docx` | `python-docx` | 保留标题样式、有序/无序列表、表格、加粗/斜体 |
| `.txt` | 内置 | 识别中文编号章节标题（`1.1 定义`、`一、背景`等）自动添加Markdown标题前缀 |
| `.md` | 直接复制 | 不做转换 |

### 2.2 扫描版与字体乱码 PDF 的 OCR 处理

文字版提取失败时自动触发 `RapidOCR`，覆盖两种失败场景：

**场景一：扫描版 PDF**

`pymupdf4llm` 输出内容不足200字符，说明PDF为图片扫描件，无可提取文字层。转而 `RapidOCR` 识别，按页拼接全文。测试案例：GB 50054-2011（低压配电设计规范）109页扫描版，提取64,249字符，条款内容完整清晰。

**场景二：自定义字体乱码**

部分国标PDF（如GB/T 13955）使用内嵌自定义字体，`ToUnicode` 映射将拉丁字母指向生僻字，导致提取结果出现 `犌犅／犜１３９５５` 等乱码，且替换字符（U+FFFD）占比为0，常规检测方法失效。随后通过检测是否出现**连续6个字符出现乱码**的情况判断文档是否受到乱码影响，如果受到乱码影响则使用`RapidOCR` 识别，效果更好。

修复效果：GB/T 13955（剩余电流保护装置安装和运行）从全文乱码恢复为正常可读内容，`ICS 29.120.50`、`GB/T 13955—2017`、`Installation and operation of residual current operated protective devices` 等标准标识和英文标题全部正确识别。

### 4.3 评测结论

当前单路向量检索在 42 文档 / 2,026 chunks 规模下，Hit@5 达到 **96%**，MRR=0.883，基础检索质量良好。主要存在两类问题：

1. **小文档被大文档语义遮蔽**（Q41/Q42）：`配网故障分析.md` 仅约 5 个 chunks，语义被体量更大的 `AI生成汇编.md` 压制，始终未进入 Top-10

## 5 下阶段改进方向

针对评测暴露的语义鸿沟问题，规划四项改进，按实施优先级排列：

### 5.1 多路检索 + RRF（召回层）

**问题**：单路向量检索对专有名词、精确数字（如"DL/T 499第3.2条"）匹配效果差；小文档的 chunks 在语义相似度排序中被大文档压制。

**方案**：同时运行稠密检索（`bge-large-zh-v1.5` 向量）和稀疏检索（BM25），用 RRF 公式融合排序：

$$RRF(d) = \sum_{i} \frac{1}{k + rank_i(d)}, \quad k=60$$

**优先原因**：不需要重建知识库，对现有架构零侵入，但召回层的改善是后续所有优化的基础。

### 5.2 Reranker 精排（排序层）

**问题**：RRF 融合后的候选切片，排序依据仍是向量相似度分数，"语义相近"≠"最有用"，同主题多文档场景下 Hit@1 不稳定。

**方案**：用 Cross-encoder（`bge-reranker-v2-m3`）对查询与每个候选切片做交叉注意力重打分，取 Top-3 送入生成。

### 5.3 假设问题预生成 HyDE（索引层）

**问题**：文档是陈述句，用户查询是疑问句，两者在向量空间天然存在偏差。

**方案**：离线建库时，用 LLM 为每个切片生成 5~10 个假设触发问题，与原始切片共享同一索引条目。

### 5.4 Agentic RAG（流程层）

**问题**：部分查询天然多跳（先查数据→再查规程→再查案例），单次检索无法覆盖。

**方案**：识别出多跳意图后启动 Agent 流程：分解子问题 → 迭代检索 → 中间推理 → 再检索 → 综合输出。仅对需要多跳推理的查询按需启用，避免对单跳查询引入不必要的延迟。
