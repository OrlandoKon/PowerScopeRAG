## 2 多路检索 + 排名融合 + 精排 实现

### 2.1 架构设计

在原单路向量检索基础上，新增三个处理阶段：

- **阶段一：双路并行检索**
  稠密向量检索（dense retrieval）与稀疏关键词检索（sparse retrieval / BM25）同时执行，各自返回扩大候选集（candidate set，数量为最终返回数的 3 倍）。dense retrieval 擅长捕捉语义相似内容，BM25 擅长匹配精确术语和数字，两路互补。

- **阶段二：倒数排名融合（RRF，Reciprocal Rank Fusion）**
  将两路检索结果按各自排名位置融合为统一得分，排名越靠前的 chunks 得分越高，排名靠后的影响力自然衰减。融合后保留扩大 candidate set 送入下一阶段，不依赖各路检索的原始相似度分数，避免两路分数量纲（scale）不同带来的偏差。

- **阶段三：交叉编码器精排（cross-encoder reranking）**
  对融合后的 candidate set，将每个 chunk 与查询拼接，通过专用精排模型 bge-reranker-v2-m3 重新打分。与 dense retrieval 独立编码查询和文档不同，cross-encoder 将二者同时输入、计算细粒度交叉注意力，精度更高，最终取前 K 个作为检索结果。

支持三种检索模式，可灵活切换：

| 模式 | 说明 |
|------|------|
| 纯向量模式 | 仅向量检索，速度最快 |
| 混合模式 | 向量 + 关键词 + 排名融合，不精排 |
| 混合精排模式 | 向量 + 关键词 + 排名融合 + 精排（默认） |

### 2.2 稀疏关键词检索（BM25）

**原理**：基于词频-逆文档频率的传统信息检索算法，用结巴（jieba）中文分词工具对文档片段（chunks）分词后建立倒排索引，查询时按词频权重打分排名。

**为什么用**：向量检索将文本压缩为固定维度向量，容易"平均化"细节，对精确数值（如"95%"、"±7%"）和专有术语（如标准编号"GB/T 45418"）匹配偏弱；BM25 逐词精确匹配，正好弥补这一缺陷。

**解决的问题**：问题中出现精确标准编号、技术参数时，纯向量检索容易返回语义相近但来源错误的文档；加入关键词检索后这类问题命中率明显提升。

**效果**：混合检索相比纯向量检索，整体命中率（命中@1）从 83% 提升至 95%。

### 2.3 倒数排名融合

**原理**：对每个文档片段，按其在各路检索结果中的排名位置赋予权重并求和：

$$score(d) = \sum_{i} \frac{1}{k + rank_i(d)}, \quad k=60$$

排名越靠前权重越高，排名 1 位贡献约 0.016，排名 20 位仅贡献约 0.013，尾部影响自然衰减。

**为什么用**：两路检索的相似度分数量纲完全不同（余弦相似度 vs. BM25 分数），无法直接相加；排名融合只看位置不看分数，消除量纲差异，融合效果更稳定。

**解决的问题**：直接相加两路分数会导致 BM25 高分文档或向量高相似度文档单方面主导结果，融合后两路结果各自的贡献更均衡。

### 2.4 交叉编码器精排

**原理**：将查询与每个候选文档片段拼接成一对，整体输入精排模型，模型通过自注意力机制同时处理查询和文档的每个词，输出精细相关性分数后重新排序。

**为什么用**：向量检索阶段查询和文档分别编码，无法感知两段文本之间的词级交互；精排模型对每一对单独计算，精度高，但不能预先计算，只适合对少量候选集做最后筛选。

**解决的问题**：融合后候选集中仍可能存在顺序偏差，精排将真正相关的文档片段调整到最前，大幅提升首位命中率（命中@1）。

**效果**：加入精排后命中@1 进一步提升，MRR 从 0.875 提升至 0.966。

### 2.5 来源多样性去重

**原理**：精排后按文档来源统计，每个文档最多保留 2 个片段进入最终结果集。

**为什么用**：同一文档切分后各片段语义高度相似，若不限制，精排后单篇文档可能占据全部 5 个槽位，导致其他期望文档根本无法出现。

**解决的问题**：直接解决了某道题目中单篇标准文档 5 个片段全部占满结果集、真正需要的另一篇文档无法被检索到的问题。

**效果**：解决后该题目命中，整体多样性显著改善。

## 5 下阶段改进方向

**存在的问题：**

- **Hit@1 精度**（检索层）：正确文档已在前5位内但未到第1位，MRR 集中在 0.33–0.50，典型场景为相邻标准（DB1331T031/032 等）之间的边界问题，cross-encoder 仍难以区分
- **语义边界模糊**（索引层）：对内容相似度高的同主题文档（如光伏线损系列），当前按固定字数切分导致 chunks 之间语义边界模糊
- **查询-文档向量偏差**（索引层）：文档是陈述句，用户查询是疑问句，两者在向量空间天然存在偏差
- **多跳查询**（流程层）：部分查询天然多跳（先查数据→再查规程→再查案例），单次检索无法覆盖

**候选方案：**

- 假设问题预生成（HyDE）：离线建库时用 LLM 为每个 chunk 生成 5~10 个假设触发问题，与原始 chunk 共享同一索引条目，缩小查询与文档的向量偏差
- Agentic RAG：识别出多跳意图后启动 Agent 流程（分解子问题 → 迭代检索 → 中间推理 → 再检索 → 综合输出），仅对多跳查询按需启用，避免对单跳查询引入不必要的延迟
